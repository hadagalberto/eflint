# EFL1001 — Query materialized before filtering or projection

**Category:** Performance · **Severity:** Warning · **Code fix:** yes

## What

EfLint reports `ToList()`, `ToArray()` and `AsEnumerable()` when they appear in the middle of an
EF Core query and are immediately followed by another LINQ query operator (`Where`, `Select`,
`SelectMany`, `OrderBy`, `OrderByDescending`, `Skip` or `Take`). The materializer must be called on
a query rooted in a `DbContext` — plain in-memory collections are not reported.

## Why

The first materializer executes the query and copies every row into memory. Operators that follow
it run on the client as LINQ-to-Objects rather than being translated into SQL, so the database
sends rows that are later discarded. Filtering, sorting and projecting in the database is
cheaper and avoids transferring unnecessary data. See
[EF Core documentation — Client vs. server evaluation](https://learn.microsoft.com/ef/core/querying/client-eval).

## Bad

```csharp
var names = db.Blogs
    .ToList()                       // all rows are loaded here
    .Where(b => b.Id > 0)           // runs on the client
    .Select(b => b.Name);

var page = db.Blogs.ToList().Skip(1).Take(2);
```

## Good

```csharp
var names = db.Blogs
    .Where(b => b.Id > 0)
    .Select(b => b.Name)
    .ToList();                      // materialize once, at the end

var page = db.Blogs.Skip(1).Take(2).ToList();
```

Keep the query as `IQueryable<T>` until the final materialization so EF Core can translate the
whole chain into SQL. AsEnumerable still reports the problem when it is followed by more query
operators, because it switches the rest of the chain to client evaluation.

## Code fix

Moves the materializer to the end of the chain and preserves its original name, so an
`AsEnumerable()` stays an `AsEnumerable()`. Fix All moves every early materializer in the document.

## Configuration

```ini
dotnet_diagnostic.EFL1001.severity = error
eflint.EFL1001.enabled = false
```
