# EFL1008 — Entity loaded only to be deleted or updated

**Category:** Performance · **Severity:** Info · **Code fix:** no

## What

EfLint reports `Remove`/`Update` on a `DbSet` when the argument is a local that was loaded earlier
in the same method from an EF Core query (`First`, `FirstOrDefault`, `Single`, `SingleOrDefault`,
`Find` and similar materializers). It also reports assigning a property of such a local, since that
is the prelude to an `UPDATE` on `SaveChanges`. Freshly created entities, parameters and entities
loaded from non-EF collections are not reported. The rule only runs when EF Core is referenced.

## Why

Loading the entity issues a `SELECT` and tracks it; the subsequent `Remove`/`Update` plus
`SaveChanges` issues a second command and a second round trip. EF Core 7+ can express the whole
operation in one statement with `ExecuteDelete`/`ExecuteUpdate`, which also avoids the change
tracker. See
[EF Core documentation — ExecuteDelete and ExecuteUpdate](https://learn.microsoft.com/ef/core/saving/execute-insert-update-delete).

## Bad

```csharp
var blog = db.Blogs.First(b => b.Id == id);
db.Blogs.Remove(blog);
db.SaveChanges();

var other = db.Blogs.Find(id);
other.Name = "new name";
db.SaveChanges();
```

## Good

```csharp
db.Blogs.Where(b => b.Id == id).ExecuteDelete();

db.Blogs.Where(b => b.Id == id).ExecuteUpdate()
    .SetProperty(b => b.Name, "new name");
```

Use the async counterparts (`ExecuteDeleteAsync`/`ExecuteUpdateAsync`) in async code. Keep the
load-then-modify form when you need the tracked entity for further work, change tracking events or
provider-side callbacks.

## Configuration

```ini
dotnet_diagnostic.EFL1008.severity = warning
eflint.EFL1008.enabled = false
```
