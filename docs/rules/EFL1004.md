# EFL1004 — Possible N+1 query pattern

**Category:** Performance · **Severity:** Warning · **Code fix:** no

## What

EfLint reports a `foreach` over the results of an EF Core query when the loop body either:

- reads a navigation property (for example `b.Posts`) that the query did not `Include`, or
- issues a query that depends on the current loop item (for example `db.Posts.Count(p => p.BlogId == b.Id)`).

Both shapes execute one database round trip per iteration instead of a single batched query. A
navigation is a property whose type is an entity declared in source, or a collection of such an
entity; scalar properties such as `Id` or `Name` are not flagged.

## Why

With N+1, the first query loads N parent rows and then each iteration lazily loads related data (or
runs a filtered query), producing N extra round trips. Latency grows linearly with the result count
and the database does most of the work in tiny queries. Eager loading with `Include`, projecting the
data you need in one query, or batching the per-item query into a single query avoids this. See
[EF Core — Eager loading](https://learn.microsoft.com/ef/core/querying/related-data/eager),
[EF Core — Loading related data](https://learn.microsoft.com/ef/core/querying/related-data/), and
[EF Core — Single vs. split queries](https://learn.microsoft.com/ef/core/querying/single-split-queries).

## Bad

```csharp
foreach (var blog in db.Blogs.ToList())
{
    // One lazy-load query per blog.
    var posts = blog.Posts;
}

foreach (var blog in db.Blogs.ToList())
{
    // One COUNT query per blog.
    var count = db.Posts.Count(p => p.BlogId == blog.Id);
}
```

## Good

```csharp
// Eager-load the navigation in the original query — one query total.
foreach (var blog in db.Blogs.Include(b => b.Posts).ToList())
{
    var posts = blog.Posts;
}

// Or project the data you actually need in a single query.
var rows = db.Blogs
    .Select(b => new { b.Id, PostCount = b.Posts.Count() })
    .ToList();

// Or batch the per-item filter into one query over the set of keys.
var ids = db.Blogs.Select(b => b.Id).ToList();
var counts = db.Posts
    .Where(p => ids.Contains(p.BlogId))
    .GroupBy(p => p.BlogId)
    .Select(g => new { BlogId = g.Key, Count = g.Count() })
    .ToList();
```

## Code fix

There is no automatic code fix for this rule. The right rewrite depends on which data the loop
actually uses and on the provider, so EfLint reports the location and leaves the choice — eager
loading, projection, or a batched query — to you.
