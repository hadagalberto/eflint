# EFL1007 — SaveChanges called inside a loop

**Category:** Performance · **Severity:** Warning · **Code fix:** yes

## What

EfLint reports `SaveChanges` or `SaveChangesAsync` when it is called from the body of a `foreach`,
`for`, `while` or `do` loop on a `DbContext`. Each call opens a transaction and performs a database
round trip, so a loop with N iterations produces N writes instead of one batched write.

## Why

EF Core tracks all changes made to the context and sends them together on a single `SaveChanges`.
Calling it per iteration pays the transaction, change-detection and network cost every time. See
[EF Core documentation — Saving data](https://learn.microsoft.com/ef/core/saving/save) and
[EF Core documentation — Performance](https://learn.microsoft.com/ef/core/performance/).

## Bad

```csharp
foreach (var blog in blogs)
{
    blog.Name = Normalize(blog.Name);
    db.SaveChanges();
}
```

## Good

```csharp
foreach (var blog in blogs)
{
    blog.Name = Normalize(blog.Name);
}

db.SaveChanges();
```

If the loop needs a database-generated key (for example it reads `blog.Id` after inserting), keep
the save inside the loop — the rule is reported without a code fix in that case. An alternative is
to restructure the code so the generated keys are not needed until after the batch has been saved.

## Code fix

When the `SaveChanges` call is a standalone statement directly in the loop body and no later
statement in that body depends on a generated key, the fix moves the statement to immediately after
the loop and keeps the loop's indentation and the document's line endings. Fix All moves every safe
`SaveChanges` in the document. Calls that are part of a larger expression (for example
`var rows = db.SaveChanges();`) or that feed generated keys into later statements are reported but
not auto-fixed.

## Configuration

```ini
dotnet_diagnostic.EFL1007.severity = error
eflint.EFL1007.enabled = false
```
